# Modelos y texturas

Entrada única para crear bloques/modelos/texturas: sigue el flujo y abre solo las herramientas de tu familia. Registros y generadores son el inventario real.

## Rutas y entrega completa

| Pieza | Ruta desde la raíz |
|---|---|
| Clases/registros | `src/main/java/net/nicomar2009/lsmmod/{block,item,entity,registry,client}/` |
| Estado de bloque | `src/main/resources/<module>/assets/lsmmod/blockstates/<id>.json` |
| Modelos | `src/main/resources/<module>/assets/lsmmod/models/{block,item}/` |
| Definición moderna de ítem | `src/main/resources/<module>/assets/lsmmod/items/<id>.json` |
| Texturas | `src/main/resources/<module>/assets/lsmmod/textures/{block,item,entity}/` |
| Idiomas | `src/main/resources/<module>/assets/lsmmod/lang/{en_us,es_es}.json` |
| Drops/recetas | `src/main/resources/<module>/data/lsmmod/{loot_table/blocks,recipe}/` |
| Herramienta de minado | `src/main/resources/<module>/data/minecraft/tags/block/mineable/` |
| Generadores/checks/renders | `tools/` |
| Fixtures necesarios / previews temporales | `tools/fixtures/`, `previews/` (fuera de Git) |

Un bloque nuevo necesita registro, ítem, estado, modelo, definición de ítem, materiales existentes o PNG nuevos, traducciones y drop; etiqueta de herramienta si corresponde. Añade recetas solo si se solicitan. ModCreativeTabs distribuye automáticamente los ítems; revisa sus reglas para elegir la pestaña correcta. Los modelos de entidades viven en Java, no en `models/block`.

Los módulos guardan estas mismas rutas bajo `src/main/resources/<module>/`; consulta [MODULES.md](../MODULES.md) para su propietario y composición. El JAR conserva las rutas e identificadores lógicos de Minecraft.

## Flujo rápido

1. Elige el patrón en la tabla inferior y abre sus enlaces; para un ID existente usa `rg '<id>' src/main/java tools`. Lee el generador: puede escribir Java/registros/idiomas/tags. Consulta [BLOCK_SPECS](BLOCK_SPECS.md) solo al cambiar comportamiento o compatibilidad.
2. Usa las referencias del usuario para fijar proporciones, materiales y silueta. Expresa medidas en píxeles: **16 px = 1 bloque**. Si solo cambia una textura, conserva geometría y colisión. No inventes funciones para decoración.
3. Reutiliza geometría padre, texturas y clases. Modifica el generador que produce el resultado y sus archivos finales; no ejecutes todos los generadores. Usa `resource_json(path, value)` de `tools/resource_json.py`: modelos/estados compactos, datos editables con sangría. Revisa `git diff` para detectar sobrescrituras ajenas al pedido.
4. Comprueba referencias, UV, materiales, alfa y modelo de inventario. Para conjuntos, verifica todas las celdas y orientaciones, bisagras/apertura, apoyo, retirada y drop único. Mantén UV continuas y elimina tapas artificiales en cortes entre celdas.
5. **Render obligatorio:** `python tools/render_block_review.py <id>`; para rejilla column/row/depth añade `--grid ancho alto fondo`, por ejemplo `school_refrigerator --grid 2 3 1`. Usa `--state facing=north clave=valor` para otros estados y `--vanilla-dir` para materiales vanilla. Dependencias: `python3 -m pip install -r tools/requirements.txt`; Blender se instala aparte para papelería. Guarda frente/laterales/dorso/ítem en `previews/<id>_review.png`; `preview_path()` crea esa carpeta cuando un render la necesita. Abre la imagen y corrige UV/costuras/materiales/alfa. Para OBJ, piezas giradas, estados dinámicos u otras rejillas usa el render de la familia; el comando exige geometría nativa sin giro. Es render externo, no prueba en Minecraft. No versiones previews, ZIPs ni copias antiguas; conserva el generador y el resultado activo.
6. Ejecuta el check existente de la familia. Si cambias selección, herencia, loaders o preparación Fusion, ejecuta también `python tools/check_optimized_model_resources.py`. No compiles según AGENTS. Documenta solo un contrato nuevo o un pendiente real.

La lógica Java lee esa misma tabla; la losa conserva FACING/OPEN y añade las propiedades de losa y retícula. Las mitades pintables aportan 0,5 bloques de cristal; los rectángulos completos se reconocen solo en vecinos cargados con la misma orientación y sin salientes. La preparación de recursos regenera los modelos de la tabla en su salida aislada antes de optimizar; no hace falta ejecutar el generador manualmente por cada entrada nueva. `projecting_window_baked_layouts.json` identifica los repartos con modelos disponibles: un JSON sin modelos correspondientes usa la retícula anterior en lugar de ocultar el cristal. Se admiten bordes verticales de media celda para combinar losas y ventanas normales; las dimensiones avanzan en medios bloques y cada hoja mide al menos 16 px por eje. El render de la familia incluye las distribuciones de la tabla en `previews/school_projecting_window_layouts_review.png`.

## Rendimiento y compatibilidad

- Texturas pixeladas a la densidad de los materiales vecinos; evita aumentar resolución para disimular UV incorrectas. Al ampliar un atlas pixel art usa vecino más cercano. Luces y sombras de la escena las produce Minecraft.
- Variantes de color heredan geometría. No dupliques modelos, texturas o clases por orientación si una rotación/tabla sirve. No copies cientos de combinaciones que solo cambian color.
- Separa contorno sencillo y colisión exacta. Reutiliza `ExactVoxelShapes`, las cuadrículas existentes, `SharedChairRotations` y `SimpleBlockOutline` según el patrón existente. Cachés físicas por geometría/ocupación, no por colores; no uses una caché por estado para geometría dependiente de vecinos.
- Conserva propiedades físicas y guardadas. Conexiones puramente visuales pueden calcularse con vecinos cargados mediante predicados Fusion; no fuerces cargas de chunks ni añadas entidades/tickers para decoración estática.
- En vidrio, separa capas solid/cutout/translucent; el vidrio transparente no debe ocultar caras opacas visibles a través de él. Cullface solo donde la cara toca el límite correcto y la conexión lo permite.
- SchoolGlazing valida el perfil del bloque actual y los extremos/celdas después de recorrer la fila. Conserva el fallback de máscara segura ante estados de render obsoletos o cristales desaparecidos, incluido el minimapa de Xaero; no accedas a `pane()` sin perfil válido. Confirmación de ese caso en Minecraft/Xaero pendiente.
- `optimize_model_resources.py` prepara originales y `src/generated/resources` en `build/generated/optimizedResources`, antes de `processResources`. Edita **los fuentes**, nunca esa salida. Comparte duplicados, padres sólidos y selectores; `prepare_high_state_models.py` exige una hoja por modelo nativo en cada raíz. La tarea admite la caché de Gradle con entradas relativas y declara también los scripts importados y sus datos; los archivos de edición excluidos del empaquetado no la invalidan. Al preparar, omite la copia de las carpetas de layouts que va a regenerar, reutiliza los JSON leídos y agrupa las escrituras de modelos.
- Fusion composite: cada lista interna elige solo el primer modelo cuya condición se cumple; un modelo sin condición termina esa lista. Componentes que deben verse simultáneamente (pared, marco, cristal) van en listas separadas. El render externo debe respetar esa selección y recorrer las raíces reales.
- Fusion 1.3.16: conserva `neoforge:obj` para OBJ; declara materiales/particle en compuestos. El MTL de pavimento usa `map_Kd gray`/`yellow` sin `#`. Un `fusion:base` usado como componente debe tener geometría real válida; no uses bases vacías ni supongas soporte de matrices `transform` en compuestos.
- Reducir modelos o selectores no prueba una mejora de tiempo. Mide arranque/JFR si se pide rendimiento; no inventes segundos ahorrados.
