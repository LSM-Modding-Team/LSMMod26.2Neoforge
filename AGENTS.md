# LSM Mod — instrucciones para Codex

- Responde en español. La petición actual del usuario tiene prioridad. Código, IDs y comentarios en inglés.
- **Módulos:** sigue [MODULES.md](MODULES.md). Solo revisa los módulos cuando el usuario lo pida; de lo contrario, no los revises.
- **Solo compilación:** `.build-tools/` reúne o enlaza JDK, dependencias, cachés (`.gradle`, Gradle compartido) y salidas (`build`). No entrar, enumerar, leer ni buscar recursivamente ahí durante tareas normales; tampoco explorar esas cachés a través de sus rutas originales. Si la tarea autoriza compilar, comando rápido: `bash tools/build/compile.sh jar --offline`; `build` también ejecuta las comprobaciones completas. Consultar `tools/build/README.md` solo si hace falta compilar o diagnosticar su entorno. No limpiar cachés ni usar `clean` en una compilación normal.
- Para crear bloques/modelos/texturas, entra directamente en [ASSETS: flujo](docs/ASSETS.md#flujo-rápido) y su tabla de generador/check/render. Para otros trabajos, usa [START_HERE](START_HERE.md).
- **No compiles localmente ni ejecutes Minecraft**, por instrucción vigente del usuario. La petición actual autoriza la compilación y las comprobaciones en GitHub Actions para entregar el JAR; esta excepción no autoriza ejecutar Minecraft ni reanudar compilaciones locales. Distingue revisión estática, render externo, compilación CI y prueba en juego.
- **Haz commit y push en la rama existente `master` en la misma respuesta**, sin pedir autorización. Trae e integra `origin/master` antes de publicar, conservando cambios de otras conversaciones. No crees ramas nuevas ni uses force-push.
- **Entrega desde GitHub Actions:** al publicar cambios, comprueba el workflow `Build` del commit exacto y enlaza su ejecución exitosa con el artefacto `lsmmod-<sha>`. No adjuntes JARs locales ni presentes una ejecución pendiente/fallida como exitosa. Conserva las comprobaciones completas de `build`, incluida `checkFurnitureOutlines`.
- **Uso disponible:** busca y llama `get_usage_limits` al comenzar continuaciones sustanciales y entre lotes relevantes. Consulta el porcentaje usado y el reinicio de los límites de 5 horas y semanal, junto con el presupuesto de contexto/turno. Avanza mientras haya capacidad útil; reserva margen para validación, documentación, revisión, commit/push y artefacto CI cuando se acerque un límite. Un lote o push terminado no obliga a parar. Si la herramienta no está expuesta en la sesión, indícalo brevemente y no inventes porcentajes ni reutilices lecturas antiguas como actuales.
- El usuario autoriza e incentiva cambios y añadidos sustanciales no descritos explícitamente cuando encajen con el mod, incluidos loot tables, comportamiento de bloques y mecánicas. Decide y actúa sin otra confirmación, documenta el diseño y valida lo afectado. Respeta IDs/NBT, objetivos y alcance actual; no continúes desarrollo de funciones si el usuario lo ha pausado.
- Reutiliza clases, materiales, modelos padre y generadores existentes. Conserva IDs, NBT y propiedades guardadas; una retirada o migración requiere petición del usuario.
- **Revisión visual obligatoria:** toda textura creada o modificada debe revisarse aplicada al modelo real mediante renders, con sus UV, materiales y transparencia. Corrige errores visibles antes de publicar; revisa también el ítem y las caras/orientaciones afectadas. Un render externo no demuestra funcionamiento en Minecraft.
- **Formas:** separa `getShape` (contorno sencillo) de `getCollisionShape` (geometría física). Usa `SimpleBlockOutline.forState` solo si depende del estado; las formas que dependen del mundo/contexto no admiten esa caché. Reutiliza cuadrículas y rotaciones; verifica orientaciones y celdas múltiples. `checkFurnitureOutlines` requiere compilar y se ejecuta en GitHub Actions como parte de `build`; no la ejecutes localmente mientras siga la prohibición.
- Ejecuta solo las comprobaciones existentes que cubran el cambio. Para lógica pura, usa `RulesCheck`; para arte/documentación, evita crear tests que solo repitan la implementación.
- Actualiza únicamente la guía afectada si cambia su contrato. No añadas historiales, registros de sesiones, documentos por cada bloque ni entradas de cambios en varios archivos. Git guarda la historia. Mantén START_HERE breve y sin cronología. No conserves backups, archivos antiguos, ZIPs de entregas ni renders en Git; los previews son temporales. Conserva únicamente recursos activos, generadores, fixtures necesarios y documentación vigente.
- Entrega un resumen corto de cambios, verificación y commit. Genera ZIP solo si se pide; excluye `.git`, `.build-tools`, `.gradle`, `build` y `run`.
